The current native Grubbery case uses the fixed original pending-app image only
as a read-only backing for a fresh offline overlay. It must preserve every
original plan/event and finish through supported lifecycle/recovery interfaces.
An acknowledged write remains uncertain until observed; no SQL repair, marker
lowering or fresh request ID substitutes for reconciliation. A timeout, unclean
shutdown or missing final lookup remains a failed whole case even when source
versions have completed.

The next project-resource slice should first expose a bounded, identity-bound
allocation/growth observation with explicit roots, shared charges, timestamps and
unknown reasons. Then persist a latched incident and reviewed resume rule for an
explicitly configured disposable project. Only after those gates should the
guard submit journaled stops to freshly verified exact members. Reuse the
supported interrupted-stop recovery path; never clear an unrelated fence, prune
a pier, infer disposability from a missing path or stop an unrelated runtime.
Thresholds must be configured explicitly; incident-specific numbers are not
universal defaults. This is planned work, not a shipped containment capability.

Before preserved DEV changes, freeze matching runtime/UI/packaging inputs and
qualify the actual previous-stable59→candidate65 upgrade, running/stopped intent,
access/history/application-state preservation, old-reader refusal and restart.
Publish only the compatibility window that was tested. Preserve manual-review
piers/history/intent during the DEV update. Production remains excluded, and no
stable publication or issue-wide completion follows from a development checkpoint.
