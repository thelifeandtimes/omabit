# One-time RC11/schema19 management upgrade

Historical RC11 runners do not implement runner-owned quiescence. An idle snapshot
does not exclude a later API request or scheduled job, so the ordinary installer
refuses to stop an online historical manager. The explicit `--offline-upgrade`
compatibility path upgrades an **existing owner-user schema19 installation** in
place. It preserves runner/instance IDs, receipts, settings, stopped intent,
running containers, pier paths, owner, access grants and SSH host identity.

## Exact one-time procedure

Use the new schema20-or-later runner executable from the accepted release/source
build, a verified rootless bundle matching that executable, and an already enrolled
operator's public key. The selected Unix owner must match
`/etc/urbit-runner/owner.json`.

For published RC.12/schema20, the existing verified bundle remains usable. For
**RC.13/schema21**, prepare a new bundle as an ordinary user before
the maintenance window; its generated guard/unit templates differ from RC.12:

```sh
/absolute/path/to/new/urbit-runner prepare-rootless \
  --output /absolute/path/to/new/rootless-bundle
```

Use that output as `--bundle` below. See the
[schema21 upgrade guide](host-compatibility-upgrades.md) for its support scope.

1. In the existing manager, let operations finish and disable scheduled routines
   for the maintenance window. Resolve reported uncertain work before proceeding.
   Other operators should stop submitting mutations during this window.
2. **As the pier-owning user**, stop only the management unit:

   ```sh
   systemctl --user stop urbit-runner.service
   ```

   Leave `urbit-docker.service` and the ships running. Do not stop the whole user
   manager, delete sockets/locks, reset state, or re-enroll any ship.
3. Run the **new executable**, using absolute paths and the installed owner:

   ```sh
   sudo /absolute/path/to/new/urbit-runner install-host \
     --owner YOUR_EXISTING_OWNER \
     --bundle /absolute/path/to/matching/verified-rootless-bundle \
     --public-key /absolute/path/to/existing/operator.pub \
     --acknowledge-host-changes --offline-upgrade
   ```

The flag is an explicit offline compatibility opt-in, not permission for the
installer to cancel work or stop a running historical manager. If work raced the
manual stop, the durable inspection refuses queued/running operations and retained
uncertainty. Before migration, restart the original manager to finish/reconcile
that work, then repeat the procedure. The refusal does not clear recovery records.

For an RC.13/schema21 target, this bridge remains management-only and installs
native package-refresh hooks after successful activation. It does not replace the
existing engine guard or perform the normal setup's package authentication. Finish
the separate [guard repair and package verification](host-compatibility-upgrades.md#old-docker2972-guard-and-package-authentication)
with the new executable before admitting new runtime work. Guard repair verifies
packages without starting/restarting the engine; any needed engine start/restart
requires separate coordination.

## What the compatibility path verifies

- The existing owner profile, management unit and operator grant match. Access,
  engine configuration and host keys are not regenerated by this upgrade path.
- The owner unit is demonstrably stopped and no foreground socket listener exists.
  The installer takes the **same** `managed/.lock` flock used by the runtime,
  excluding concurrent management startup through migration and publication.
- The existing SQLite database is opened read-only for initial inspection, as its
  existing owner. Schema19, stable runner identity, completed receipts and absence
  of unresolved work are required. Missing, unknown and future schemas are refused.
- The previous root-owned installed executable must have static Linux/amd64 Go
  runner provenance and report schema19. Its `state-schema` command runs only after
  dropping privileges, in a fresh chroot containing just the read-only executable,
  with an isolated network namespace. Unsupported isolation or executable format
  is a refusal, not a fallback to executing the artifact as root.
- Verified old/new executable generations and a root-owned activation journal are
  durable **before** database changes. The normal migration implementation and the
  new management fence commit in **one SQLite transaction**. SQL work runs as the
  existing owner, preserving database/WAL ownership. No instance or receipt bodies
  are rewritten by this compatibility transaction.
- The new executable is published and synced while the runtime flock is held.
  After releasing that lock, the installer starts management and verifies service
  invocation, socket peer PID, executable hash, identity, schema and retained fence.
  Only verified activation releases admission. Ordinary running/stopped intent
  and normal reboot-resume policy continue after release.

## Recovery after interruption

Rerun **the same command with `--offline-upgrade` and the same new executable**.
The installer reacquires locks and resumes from durable evidence, including when
the new manager has a different PID/invocation or a release acknowledgement was
lost. An exact-version repeat after completion verifies the online manager without
stopping it. Later new-to-new updates use the ordinary command without this flag.

If the verified manager has exited, the retry proves the service is stopped with
no foreground listener and starts the expected installed generation. It never
stops or restarts an already-live manager just to replay completion. Online updates
apply the same start-only recovery to verified activation and compatible rollback.

For a normal **new-to-new online update** still at `prepared`, the acquire request
may have committed even if its acknowledgement was lost. If that previous manager
has exited, the same-command retry proves that its retained executable is still
installed, the unit is stopped, and no listener survives, then starts that unchanged
previous generation. It verifies the service/peer/build/identity and replays the
**same acquire token** before any target activation. A live previous manager is
not restarted. If acquire never committed and normal startup admitted work, acquire
refuses as busy and leaves that manager running; let the work finish and retry.
An already-released token or a foreign fence is refused rather than treated as
acquired or silently replaced. This prepared-stage recovery is not a schema19
rollback and does not change fresh installation when there is no previous generation.

A release can commit before its acknowledgement is lost. The new manager may then
accept work and exit before finishing it. For a `verified`/`complete` schema20
continuation, the installer holds the runtime lock and checks the exact journal
token, runner ID, schema and installed generation. When that token is already
released, queued/running work and recovery records are left intact for the **new
manager's normal startup reconciliation**; the schema19 initial-idle prerequisite
is not reapplied. A still-held fence continues to require idle state and stays held
through restart until verified release. Wrong-token/identity/schema/build evidence
is refused without changing the fence. The original schema19 runner is never a
recovery target after migration.

Recovery artifacts are:

- `/etc/urbit-runner/management-activation.json` (root-owned, mode `0600`);
- `/usr/local/lib/urbit-runner/generations/<sha256>/urbit-runner` and `contract.json`;
- the existing owner database's `meta.management_update_v1` fence.

The journal's `target.sha256` identifies the retained **new** installer executable
that can be used for the same retry command if the original download is unavailable.
Stages `offline-prepared` and `offline-fenced` precede executable publication;
`starting`, `verified`, and `complete` share the online activation/release contract.

After the schema20 transaction commits, the retained schema19 executable is for
provenance/recovery analysis only: **automatic schema19 rollback is forbidden**.
An activation failure preserves the journal and fence for a forward retry. Never
restore an old binary by lowering `user_version`, delete the journal/fence to bypass
admission, restore an old database over current state, reset, or re-enroll.

This support path covers the owner-user schema19 installation and its journaled
continuations. Other historical schemas, custom unit invocations and legacy
dedicated-account migrations require their own supported compatibility work.
Tests exercise real temporary SQLite schema19 databases, locks, transactional
rollback and injected activation interruptions. They do not constitute real
power-loss, namespace-isolation-on-every-host, or live-ship upgrade qualification.
