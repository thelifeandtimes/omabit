# Running-peer application recovery fixture

The separately selected running-peer fixture keeps the original ~nec process alive
while ~zod completes two queued same-pier replacements. All eight application
writes use ~nec as sender, including after each receiver replacement. Four phase
observations and final cleanup require unchanged peer container, owner/config,
network attachment, PID, start timestamp and restart count. Lifecycle adapters also
retain their existing complete project observations. The peer receives no queued
Stop; final shutdown uses only its exact fixture-owned ID. This deliberately does
not claim that stale initial readiness authorizes a new operation after a peer
changes generation.

The existing stopped-peer fixture is preserved as the default; appliance23 is
already frozen and contains none of these changes. A new explicit entry token and
`--exercise-project-live-peer` flag select this mode, requiring application-state
and member-launch flags. The host guard refuses before private file/engine access.

Twelve phase/transport checks pass, including remote sender routing in all phases.
Narrow Go race checks pass in1.030s: unchanged peer accepted, eight resource/process
changes and absent peer refused; six VM entries skip without their tokens. Vet and
explicit host/appliance refusals pass. This is source qualification only, with no
persistent-format or product-runtime change. The new fixture still needs a frozen
appliance and independent runtime verification. No installed ship or desktop
participated.
